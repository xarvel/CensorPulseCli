# Эксперименты Этапа 1

## Стенд

- тестовая vantage: облачная точка в Москве (RU-cloud);
- контрольная vantage: контрольная точка в ЕС;
- один таргет: чистый облачный таргет (EU);
- матрица: OpenVPN reset, TLS ClientHello и random payload на same IP/port; TCP и UDP; обязательная стадия application reply.

Raw результаты 08.09 хранятся во внутренних заметках стенда (не в репозитории); в этой спецификации фиксируются выводы, необходимые Этапу 2.

## 08.09: чужие VPN Gate endpoints

С российской vantage TCP connect к части адресов проходил, но после любого payload наступал timeout. OpenVPN, TLS и random bytes падали одинаково. С контрольной точки в ЕС OpenVPN reset и TLS получали протокольный ответ. Следовательно, эти данные совместимы с блокировкой endpoint/data plane, но **не** доказывают fingerprint-блокировку OpenVPN. Два ранних ложных вывода были пойманы именно paired control.

На одном адресе TCP connect был стабильно примерно на 100 ms быстрее ICMP RTT. Это совместимо с поддельным SYN-ACK от middlebox, но без TTL/pcap остаётся гипотезой.

## 08.09: собственный чистый облачный таргет

Из Москвы и с контрольной точки в ЕС получен корректный OpenVPN `SERVER_RESET` на TCP/1194, TCP/443 и UDP/1194. TLS/random на OpenVPN listener штатно закрывались сервером. Дифференциала между vantage не было: OpenVPN к свежему собственному IP на этом пути не блокировался.

Ограничение: облачная точка в Москве — не абонентская сеть и может обходить часть пользовательской инфраструктуры ТСПУ. Вывод нельзя переносить на МТС/Билайн/домашний ISP.

## 10.09: повтор воспроизводимости

Матрица повторена нативно с обеих vantage. Результат совпал:

| Тест | Контроль (ЕС) | Москва (RU-cloud) |
|---|---|---|
| OpenVPN reset TCP/1194 | SERVER_RESET | SERVER_RESET |
| OpenVPN reset TCP/443 | SERVER_RESET | SERVER_RESET |
| OpenVPN reset UDP/1194 | SERVER_RESET | SERVER_RESET |
| TLS/random на OpenVPN listener | EOF | EOF |
| TCP/22 sanity | DATA | DATA |

RTT: контроль (ЕС)→таргет connect около 40–50 ms, Москва→таргет около 40–60 ms; UDP OpenVPN response около 30–40 ms. Контрольная точка жива, поведение двухдневной давности воспроизводится.

## Выводы для реализации

1. `connect=ok` нельзя считать успехом: результат обязан иметь стадии `connect`, `write`, `first_byte`, `protocol_proof`.
2. Валидный protocol payload всегда сравнивать с random и другим протоколом на том же сокете.
3. Клиентский результат объединять с серверным observation; иначе silent timeout не локализуется.
4. Vantage должна быть нативной: SOCKS CONNECT может подтвердить соединение до фактического дозвона к target.
5. Для окончательного RST/SYN-ACK attribution нужен root capture на исследовательской vantage; мобильный MVP должен честно выдавать лишь `suspected`.
6. Нужна отдельная абонентская RU vantage перед заявлениями о поведении мобильных/домашних сетей.

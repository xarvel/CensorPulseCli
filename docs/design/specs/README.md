# CensorPulse — Этап 1: исследование и спецификация пробы

Статус: завершён первый исследовательский проход, 2026-09-10.

## Артефакты

Литературный обзор по протоколам (`01-tcp-ip-middlebox`, `02-tls`,
`03-http-dns`, `04-udp-quic-wireguard`, `05-vpn-proxy-protocols`) лежит в
основном репозитории CensorPulse в `docs/research/`, не в этом.

- `TEST-CATALOG.md` — нормативный каталог тестов и ожидаемые ответы.
- `WIRE-PROTOCOL.md` — управляющий протокол, сессии, nonce и серверные наблюдения.
- `CLASSIFICATION.md` — правила вердиктов и confidence.
- `DOCKER-PROBE.md` — требования к Docker-контрольной точке и безопасность.
- `EXPERIMENTS.md` — проведённые замеры и ограничения выводов.

## Главные решения

1. Один FAIL ничего не доказывает. Каждый протокольный тест выполняется как дифференциальная группа: валидный протокол, случайный payload и базовый echo на том же IP/порту; порядок рандомизируется.
2. TCP connect `ok` не означает доступность: обязательна проверка application payload.
3. Клиентский таймаут сам по себе не отличает network drop от server drop. Серверный журнал с `session_id/test_id/nonce` — обязательная половина доказательства.
4. Сервер не является VPN/прокси общего назначения. Все протоколы заканчиваются на локальном nonce-echo/blackhole; egress запрещён.
5. Основной продуктовый результат — карта наблюдаемого поведения, а не утверждение о конкретном DPI-вендоре.

## Граница применимости

Один чистый IP хорошо измеряет protocol/port/fingerprint policy и модификацию пути. Он не может надёжно доказать блокировку конкретного чужого домена, когда правило цензора привязано одновременно к домену и IP/ASN назначения. SNI/Host с известными trigger-строками на нашем IP измеряет чувствительность middlebox, но отрицательный результат не означает, что реальный сайт доступен.
